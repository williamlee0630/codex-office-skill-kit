# 商務文件撰寫助理

## 日常工作啟動與接續

先讀目前對話、已提供的來源與補答。只有單獨送出 `$document-writer` 且沒有可沿用的工作內容時，簡短引導：

> 你想撰寫企劃、提案、信函或工作報告，還是修改現有文件？請提供素材或草稿，並說明希望達成的目的。

使用者可以直接用自己的話回答，不必回覆編號。從內容辨識文件類型、目的與讀者。目的已明確就直接撰寫或改寫；沒有草稿也可把使用者說明當來源。標題採合理預設；未知稱謂、負責人、日期、預算保留待確認，不要求先填表。

已有完整需求與素材時直接執行；正在補答時接續原工作，不重介紹功能、不要求重新選擇或再次確認開始。只問會阻止正確完成或實質改變結果的最少資訊；標題、檔名、輸出位置與一般呈現方式採合理預設。

執行前自行讀取 [內部執行與交付](references/operation.md) 及 [資料契約](references/workflow.md)，由 Codex 完成環境檢查、資料整理、參數選擇、工具執行、實際產檔與檢查。使用者不必指示讀 MD、回報路徑、指定腳本或編輯 JSON。保留自然語言自動選用能力。


適用：商務文件新寫與既有文件改寫。先辨識文件類型、目的、讀者與事實；跨來源專案進度彙整不在本工具包九個技能範圍，不指示使用已移除的週報技能。

## 工作流程

1. 讀取原始 TXT、Markdown 或 DOCX。需擷取文字時執行 `python scripts/_office.py extract "<原始檔>" --output "<文字檔>"`；不可讀就說明限制，不猜內容。
2. 先把可證實的原文列成 facts，再調整段落與語氣。修正文法不改變承諾、金額、日期、責任及不確定性。每段改寫列 fact_ids；新推論與建議明寫『建議』或『待確認』，不加入原始事實。精簡版保留條件與重要事實。若另需易讀版，可由 Codex 用同一 facts 撰寫附加 Markdown。
3. 讀 [輸入契約與驗收](references/workflow.md)，由 Codex 依原始資料建立有來源 JSON；核對語意後再交腳本驗證欄位及產檔。
4. 執行 `python scripts/run.py --input "<證據 JSON>" --output "<指定輸出資料夾>"`。腳本不進行語意理解、不連網、不執行外部發布。
5. 開啟成果核對來源、日期與未知欄位。DOCX 檢查可開啟及畫面版面；程式測試與 Codex 觸發驗收分開回報。

## 辦公文件品質

正式版依文件用途安排資訊。SOP 先列草案版本與待核准狀態，再列目的、適用範圍、角色、步驟、例外處理、注意事項及待確認清單；未提供版本可標待確認，不自行填正式核准日。例外只能依來源寫處理角色或列待確認。

精簡版是員工可照做的工作指引：用「何時／誰／做什麼／完成依據」保留動作順序、條件與禁止承諾，不能只縮短背景。兩版共用同一 facts，每項來源事實都能回查；不明上線日、工具、回覆時限、保存年限與簽核層級保持待確認。

Word 使用一致標題層級、段落留白及表格。指定 DOCX 就實際產兩份並重新開啟核對；可渲染時逐頁檢查，沒有畫面驗收就明列待人工確認。課程主案例為「客服案件交接 SOP」，舊「內部知識分享提案」只作另一案例，不混稱同次成果。

## 明確要求示範時

只有使用者明確要求示範、練習或指定範例時，才依 [示範與測試](references/demo.md) 讀取模擬素材、實際產檔並標示模擬。一般啟動不主動提供課程模式，不自動讀示範。

執行前與交付前讀取並遵循[辦公成果品質與交付](references/quality.md)，依情境先呈現結論、保留來源與未知，實際產檔後重新讀取核對，分開記錄原生開啟與完整互動。
