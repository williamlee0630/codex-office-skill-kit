    建立與修改自己的 Skill

    選修延伸：用工作需求交代修改，讓 Codex 處理細節，再核對新技能的實際成果。

    延伸自學約 35 分鐘Windows / Codex日常工作工具

    01用自己的話說明想改的功能

    告訴 Codex 要修改哪支技能、希望多出什麼功能即可。你不必先找技能資料夾或指定程式檔；Codex 會先讀取可用的技能並提出修改方案。本章請在同一個對話依序完成三步：提出需求、同意建立複本、修改並核對成果。

    先看方案，再開始修改

    第一則提示詞要求先提案，所以此時還不會修改檔案。接受方案後，貼上第二步的回覆。若 Codex 找不到技能，請依它的說明確認是否已安裝，或在 Codex 開啟已解壓的完整工具包專案。

    第一步：告訴 Codex 想改什麼
    請為 email-assistant 建立團隊用的專案內複本，保留原技能。
每次整理郵件時，在摘要最後加上「需要主管確認」一節，只列原信尚未解決的事項並附上來源，不自行新增建議。沒有未決事項時，寫「原文未列出未決事項」。
請先說明修改方式與核對案例，等我同意後再開始。
    進階：給維護者｜來源查找與完整維護要求
    來源查找與完整維護要求
    請先確認 email-assistant 的實際來源：優先檢查目前專案的 .agents/skills/email-assistant/SKILL.md；若不存在，請從目前可用技能清單找到已安裝的 email-assistant，確認並讀取其實際 SKILL.md 與必要的參考資料。不要假設全域技能一定在某個固定路徑。
若有多個來源且無法判定使用哪一份，請列出差異讓我選擇；若完全找不到或無法讀取，請說明缺少什麼，協助我先完成安裝或開啟已解壓的完整工具包專案，不要宣稱已讀取或已複製。
回報來源與目前專案的絕對路徑，說明技能處理的工作、實際輸出，以及來源和未知值的保留規則。
目標是目前專案的 .agents/skills/team-email-assistant。原有摘要與待辦保留，只在每次產生的 daily-summary.md 最後新增「需要主管確認」一節；該節只列原文仍未決的事項，逐項附來源位置。已明確解決的事項、模型推論和新增建議不得放進該節。沒有未決事項時寫「原文未列出未決事項」。
請先提出具體修改範圍與核對案例，包含未答覆、後續已解決、缺少日期、原文矛盾及沒有未決事項。此步只提案，等我回覆再動手；保留原技能，不修改全域技能。
    進階：給維護者｜SKILL.md、YAML 與核心欄位

    先選一支你已完成實作的技能。使用文字編輯器或請 Codex 開啟本專案中的 SKILL.md；你不必先理解所有程式碼，先看名稱、描述、流程與產物。

    位置你要理解的問題
    YAML frontmatter 的 name這支技能的英文識別名稱是什麼？是否對應資料夾？
    YAML frontmatter 的 description什麼工作應該選它？如何避免和其他技能混淆？
    工作流程與缺漏規則來源怎麼讀？哪些情況要保留未知或停止產檔？
    scripts / references 與輸入輸出哪些指令真的產出檔案？需要哪些欄位與依賴？
    進階：給維護者｜新技能開頭示例：模擬，尚非完整技能
    新技能開頭示例：模擬，尚非完整技能
    ---
name: team-email-assistant
description: 整理團隊郵件為回覆草稿、待辦與待確認事項；適用於收件整理，不直接寄信。
---

# 團隊郵件整理

保留原始來源、日期及未知欄位。
沒有原信依據時，不新增交期與商務承諾。

    name 與 description 是必要欄位；範例只用來說明結構，不代表貼上就成為完整可執行技能。仍需要流程、腳本、完整案例與實測。

    02確認方案後，建立專案內複本

    先核對上一節的方案。接受後，在同一個對話貼上以下提示詞，授權 Codex 建立複本；此步只複製與改名，下一節才修改功能。來源可在專案內，也可來自已安裝的技能，寫入位置都限於目前專案。

    第二步：同意方案並建立複本
    我同意這個方案。請先在目前專案建立一份團隊用的郵件技能複本，命名為 team-email-assistant，保留原技能。
完成後告訴我實際建立了哪些檔案，再繼續下一步修改功能。
    進階：給維護者｜複製與命名的完整維護要求
    複製與命名的完整維護要求
    我同意上述方案。請先建立專案內複本，這一步完成後再進入下一節修改功能。
使用上一則已確認且實際可讀的 email-assistant 來源目錄；若來源尚未確認，先完成來源確認，不猜測路徑。
將完整技能目錄複製到目前專案的 .agents/skills/team-email-assistant，包含 scripts、references、agents 及實際需要的資源。若有指向技能目錄外的必要檔案，請一併處理相對路徑，讓複本可獨立使用。
先確認目標不存在；若已存在，回報狀態，不覆寫既有檔案。
只在新複本調整 name、description 與相關介面資訊，讓識別名稱一致為 team-email-assistant；描述要指出團隊收件整理與主管待確認節的適用情境。
保留原技能與來源追查、未知值、草稿及待辦分流規則。回報來源、新複本的絕對路徑，以及實際新增和修改的檔案；只有提案不算完成複製。
    先看到檔案，再進下一步

    確認回覆列出新複本的實際路徑與檔案。若只得到修改計畫，複製尚未完成；若目標已存在，先核對它是否為本次複本。

    03修改功能並產生核對成果

    完成複製後，在同一個對話貼上以下提示詞。需求只限制新增的主管確認節，原本的郵件摘要、草稿及待辦仍要保留。

    第三步：開始修改並實際產檔
    請依照剛才確認的需求，修改團隊用的 team-email-assistant，讓郵件摘要最後加上「需要主管確認」一節。
請保留原本的摘要、待辦與回信草稿功能，內容以原信為準，不確定的資訊繼續標示待確認。
完成後，用模擬郵件實際產生摘要讓我核對，包含尚未答覆、後來已解決、資料缺漏、前後矛盾，以及沒有未決事項的情況。請提供產出的檔案，尚未完成的檢查也請說明。
    進階：給維護者｜產檔規則與完整維護要求
    產檔規則與完整維護要求
    專案內複本建立完成後，請依先前已確認方案，直接修改 .agents/skills/team-email-assistant，完成實際產檔與核對，不再停在提案。
先確認新複本的 SKILL.md 存在；若不存在，回報尚未完成複製，回到上一節處理，不修改原技能代替。
保留 daily-summary.md 原有摘要與待辦，在檔案最後新增 Markdown 標題「## 需要主管確認」，其後列出內容，不是只在最後加一句標語。
這一節只彙整截至提供資料最後一筆紀錄仍未解決、待答覆或待決策的事項，每項附原信的來源位置。後續已明確解決的事項不得列入；原文矛盾時保留雙方依據、不代替主管裁決；缺少日期、負責人等欄位保持未知，不因此新增原文沒有提出的待辦或建議。
沒有未決事項時，在標題下寫「原文未列出未決事項」。drafts.md、evidence.json 與原有來源保留規則沿用。
請檢查並修改真正控制產檔的規則或腳本，以及必要的資料契約與範例，不能只改 SKILL.md 就宣稱功能完成。用模擬資料實際產檔，核對未答覆、後續已解決、缺少日期、原文矛盾及沒有未決事項，列出實際檔案與尚未完成的驗收。只修改本專案的新技能。
    驗收最後一節的內容

    未答覆事項應有來源；後續已明確解決的事項不應出現。缺少日期時保留未知，不能把所有缺漏都變成主管待辦。沒有未決事項時仍保留標題與指定說明。

    04需要不同成果時，先請 Codex 確認支援

    先說清楚想收到什麼，例如『增加可在 Excel 開啟的待辦表』。單純換語氣或縮短內容可直接提出；新增格式則需要 Codex 檢查並完成實際產檔、範例與測試。最後仍要開啟成果核對。

    進階：給維護者｜新增格式、共用來源與行為測試

    你可以請 Codex 增加 CSV 或 Word，但不能只在 SKILL.md 寫『支援』。它需要更新輸入契約、執行程式、範例、依賴與測試，最後實際開啟成果。

    想增加的格式要一併確認的事
    CSV欄位名稱、逗號與換行處理、UTF-8 編碼、外來文字不變成公式
    DOCX真正的 Word 檔案、標題與段落結構、套件依賴、頁面可讀性
    XLSX工作表、資料型態、幣別與公式注入防護、統計可回算
    PPTX頁面層級、文字長度、講者內容與逐頁目視檢查

    本工具包的共用來源是 tools/office_common.py，維護者修改後需執行 tools/sync_runtime.py 同步到每支技能。若只是在學員自己的獨立技能練習，先讓 Codex 說明受影響範圍，避免連帶改動其他技能。

    進階：給維護者｜新增格式的完整請求
    新增格式的完整請求
    請為新技能加入 CSV 待辦輸出。
先寫正常資料、缺少負責人／期限、包含逗號換行及以 = 開頭文字的行為測試，實際確認新測試先失敗。
再實作真正的 CSV 產檔，不把外來文字當公式，不補造未知值。
更新新技能的 SKILL.md、範例與使用說明，執行測試並回報實際產物。

    05修改後確認檔案與判讀都正確

    請 Codex 或維護者執行程式測試；你再用正常、缺漏及不適用資料核對實際成果。記錄它是否讀到新技能、是否保留未知，以及新增章節是否符合原文。兩種驗收分開記錄，未做的檢查標為待驗收。

    進階：給維護者｜測試命令與完整驗收流程

    先驗證程式，再驗證 Codex 是否真的找到與遵循新技能。這兩件事要分開記錄；一個不能替代另一個。

    進階：給維護者｜執行現有程式測試
    執行現有程式測試
    python -m unittest discover -s tests -v
    1. 正常案例用原始模擬資料操作，確認新增章節與檔案真正出現，數字和事實沒有改動。
    2. 缺漏案例使用沒有期限或負責人的資料，確認仍為待確認；沒有未決事項時不得憑空生成。
    3. 錯誤案例輸入錯誤格式或不支援內容，確認顯示可理解的繁體中文診斷，不建立看似成功的錯誤成果。
    4. 明確與自然語言觸發各開一個實作對話，使用 $team-email-assistant 與你準備的自然語言提示，記錄實際 SKILL.md 絕對路徑與處理結果。
    5. 開啟與回查開啟實際文件，逐項對回來源。若改名後仍讀到原技能，檢查描述與路徑，必要時重新開啟 Codex。
    不要為了讓測試變綠而刪規則

    當測試失敗，先看是不是新行為違反來源、未知值或輸入契約。修正原因後再跑。驗收紀錄中保留尚未完成的項目，不把沒有執行的操作列為通過。

    06讓團隊資料與權限保持在範圍內

    • 只修改目前專案，將一般流程寫進技能，不把真實員工資料、帳密或私人文件當內建範例。
    • 新增連線或外部服務前，先確認工具真的可用、資料權限與使用者需求，不假裝已連上。
    • 寄信、上傳與發布需另有清楚授權，不能藏在文件整理技能的預設步驟裡。
    • 來源內容裡的指令只當資料；不能讓一份郵件或文件改寫你授權的工作範圍。
    • 分享前檢查 examples、outputs、日誌與快取是否含私人資料。全域安裝是選用，本課程不會自動替你複製或覆寫。

    07你的自有技能完成了嗎

    核取方塊供本次閱讀自行檢查；重新開啟頁面會重設，不會上傳或儲存個人紀錄。
