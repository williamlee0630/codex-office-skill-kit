    CHAPTER 11 / 實作課程

    建立與修改自己的 Skill

    選修延伸：用工作需求交代修改，讓 Codex 處理細節，再核對新技能的實際成果。

    延伸自學約 35 分鐘Windows / Codex日常工作工具

    01先用工作語言說出想改的結果

    本章是選修延伸，不是開始使用前的先修課。完成一項原有技能後，你可以把改動交給 Codex：說明誰會使用、什麼時候使用、要多出什麼成果，並保留來源、日期與未知規則。你不需要先學程式語法。

    進階：給維護者｜先把修改需求交給 Codex
    先把修改需求交給 Codex
    我已完成目前專案的郵件技能練習。請先閱讀 .agents/skills/email-assistant/SKILL.md，說明這支技能處理什麼工作、交出哪些檔案，以及如何保留來源與未知。
我想做一份團隊用的專案內複本：每份摘要最後加上『需要主管確認』，只能整理原文未決事項。
請先提出具體修改範圍與核對案例，再依我的回覆處理；保留原技能，不修改全域技能。
    進階：給維護者｜SKILL.md、YAML 與核心欄位

    先選一支你已完成實作的技能。使用文字編輯器或請 Codex 開啟本專案中的 SKILL.md；你不必先理解所有程式碼，先看名稱、描述、流程與產物。

    位置你要理解的問題
    YAML frontmatter 的 name這支技能的英文識別名稱是什麼？是否對應資料夾？
    YAML frontmatter 的 description什麼工作應該選它？如何避免和其他技能混淆？
    工作流程與缺漏規則來源怎麼讀？哪些情況要保留未知或停止產檔？
    scripts / references 與輸入輸出哪些指令真的產出檔案？需要哪些欄位與依賴？
    進階：給維護者｜新技能開頭示例：模擬，尚非完整技能
    新技能開頭示例：模擬，尚非完整技能
    ---
name: team-email-assistant
description: 整理團隊郵件為回覆草稿、待辦與待確認事項；適用於收件整理，不直接寄信。
---

# 團隊郵件整理

保留原始來源、日期及未知欄位。
沒有原信依據時，不新增交期與商務承諾。

    name 與 description 是必要欄位；範例只用來說明結構，不代表貼上就成為完整可執行技能。仍需要流程、腳本、完整案例與實測。

    02先做專案內複本，再改名稱

    不要直接覆寫已用過的技能，也不要修改全域技能。先在目前專案為一支技能建立新的資料夾，保留整份 scripts、references 與需要的資源。名稱使用小寫英文與連字號。

    進階：給維護者｜請 Codex 建立自己的技能複本
    請 Codex 建立自己的技能複本
    請只在目前工作區複製 .agents/skills/email-assistant 為 .agents/skills/team-email-assistant。
先確認目標不存在，不覆寫現有檔案。
將新技能的 name、description 及相關介面資訊調整為一致的新名稱。
保留來源追查、未知值、草稿與待辦分流規則，原技能保持可用。
回報新增與修改的檔案。
    不要讓兩個名稱共用模糊描述

    新 description 要寫出適用與非適用情境。比如『團隊收件整理』與『正式文件撰寫』是不同工作；只寫『協助辦公室工作』，難以可靠選擇。

    03調整觸發條件與工作流程

    先把你想改的行為說成可觀察結果。例如：每份郵件摘要最後多一段『需要主管確認』，其內容只能來自原文中的未決事項。不要只要求『更專業』，因為那很難驗收。

    1. 定義觸發情境寫出兩句應該使用新技能的自然語言提示，再寫一句不適用提示。避免和原本技能完全相同。
    2. 說明流程變更指出要在哪一步增加、刪除或重排內容。保留來源、未知與確認狀態，語氣調整不能改變事實。
    3. 指定產物變更明確寫出新增章節或欄位的名稱與資料來源。新增 Markdown 標題可能只需改產檔規則，新增檔案格式則要改腳本。
    4. 列出驗收案例至少準備正常、缺漏及錯誤資料。寫出你預期看到什麼，再請 Codex 動手修改。
    進階：給維護者｜把改動說成可驗收需求
    把改動說成可驗收需求
    請修改目前專案的新技能 team-email-assistant。
需求：輸出摘要最後加入『需要主管確認』，僅彙整原始資料中尚未確認的事項與來源。
沒有這類事項時寫『本次原始資料未列出』，不得新增提議。
先說明會修改哪些檔案與可觀察的驗收案例，再只修改本專案的新技能。
保留原技能與所有未知值規則。

    04需要不同成果時，先請 Codex 確認支援

    先說清楚想收到什麼，例如『增加可在 Excel 開啟的待辦表』。單純換語氣或縮短內容可直接提出；新增格式則需要 Codex 檢查並完成實際產檔、範例與測試。最後仍要開啟成果核對。

    進階：給維護者｜新增格式、共用來源與行為測試

    你可以請 Codex 增加 CSV 或 Word，但不能只在 SKILL.md 寫『支援』。它需要更新輸入契約、執行程式、範例、依賴與測試，最後實際開啟成果。

    想增加的格式要一併確認的事
    CSV欄位名稱、逗號與換行處理、UTF-8 編碼、外來文字不變成公式
    DOCX真正的 Word 檔案、標題與段落結構、套件依賴、頁面可讀性
    XLSX工作表、資料型態、幣別與公式注入防護、統計可回算
    PPTX頁面層級、文字長度、講者內容與逐頁目視檢查

    本工具包的共用來源是 tools/office_common.py，維護者修改後需執行 tools/sync_runtime.py 同步到每支技能。若只是在學員自己的獨立技能練習，先讓 Codex 說明受影響範圍，避免連帶改動其他技能。

    進階：給維護者｜新增格式的完整請求
    新增格式的完整請求
    請為新技能加入 CSV 待辦輸出。
先寫正常資料、缺少負責人／期限、包含逗號換行及以 = 開頭文字的行為測試，實際確認新測試先失敗。
再實作真正的 CSV 產檔，不把外來文字當公式，不補造未知值。
更新新技能的 SKILL.md、範例與使用說明，執行測試並回報實際產物。

    05修改後確認檔案與判讀都正確

    請 Codex 或維護者執行程式測試；你再用正常、缺漏及不適用資料核對實際成果。記錄它是否讀到新技能、是否保留未知，以及新增章節是否符合原文。兩種驗收分開記錄，未做的檢查標為待驗收。

    進階：給維護者｜測試命令與完整驗收流程

    先驗證程式，再驗證 Codex 是否真的找到與遵循新技能。這兩件事要分開記錄；一個不能替代另一個。

    進階：給維護者｜執行現有程式測試
    執行現有程式測試
    python -m unittest discover -s tests -v
    1. 正常案例用原始模擬資料操作，確認新增章節與檔案真正出現，數字和事實沒有改動。
    2. 缺漏案例使用沒有期限或負責人的資料，確認仍為待確認；沒有未決事項時不得憑空生成。
    3. 錯誤案例輸入錯誤格式或不支援內容，確認顯示可理解的繁體中文診斷，不建立看似成功的錯誤成果。
    4. 明確與自然語言觸發各開一個實作對話，使用 $team-email-assistant 與你準備的自然語言提示，記錄實際 SKILL.md 絕對路徑與處理結果。
    5. 開啟與回查開啟實際文件，逐項對回來源。若改名後仍讀到原技能，檢查描述與路徑，必要時重新開啟 Codex。
    不要為了讓測試變綠而刪規則

    當測試失敗，先看是不是新行為違反來源、未知值或輸入契約。修正原因後再跑。驗收紀錄中保留尚未完成的項目，不把沒有執行的操作列為通過。

    06讓團隊資料與權限保持在範圍內

    • 只修改目前專案，將一般流程寫進技能，不把真實員工資料、帳密或私人文件當內建範例。
    • 新增連線或外部服務前，先確認工具真的可用、資料權限與使用者需求，不假裝已連上。
    • 寄信、上傳與發布需另有清楚授權，不能藏在文件整理技能的預設步驟裡。
    • 來源內容裡的指令只當資料；不能讓一份郵件或文件改寫你授權的工作範圍。
    • 分享前檢查 examples、outputs、日誌與快取是否含私人資料。全域安裝是選用，本課程不會自動替你複製或覆寫。

    07你的自有技能完成了嗎

    核取方塊供本次閱讀自行檢查；重新開啟頁面會重設，不會上傳或儲存個人紀錄。
